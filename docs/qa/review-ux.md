## BLOCKER

### B1. Claude Desktop / .mcpb users never get the helper, and the docs say the opposite
- `mcpb/manifest.json:10` ("Run the bundled `c3d_install_bridge` tool once") vs `packages/server/src/tools/health.ts` (`install(rt, { installHelper: false })`). The tool installs only the macro and runtime. `c3d_new_document`, `c3d_capture_viewport` and `c3d_make_editable` need the helper, and only the CLI `install` installs it. A .mcpb user has no `npx`, so they have no way to install it, and they are never told.
- README:19 says "one command ... installs the bridge macro + runtime and the helper app", and SETUP:8 says "installs the helper if present". A newcomer cannot tell whether the helper was installed. The helper is copied only if `packages/server/assets/helper` exists, and `ls packages/server/assets` shows it does not in the repo. It is created at `prepack`.
- Fix (manifest long_description): "Controls Cheetah3D 8.1.3 on macOS. After installing, ask Claude to run `c3d_install_bridge`, then restart Cheetah3D. This installs only the in-app bridge. For new-document, viewport capture and faster, safer menu automation also install the Accessibility helper: `brew install --cask megatih/c3d-mcp/c3d-bridge-helper` (or run `npx -y c3d-mcp install` in Terminal), then enable it in System Settings > Privacy & Security > Accessibility."
- Fix (code or doc): make `c3d_install_bridge` also install the helper, or state in its description: "Does not install the helper app; use `c3d-mcp install` for that."
- Fix (SETUP:8): replace "installs the helper if present" with "installs the helper app if this package contains it; `doctor` shows 'helper' as ok or degraded. If degraded, run `brew install --cask megatih/c3d-mcp/c3d-bridge-helper`."

### B2. Accessibility step cannot be completed as written
- README:15-16 and SETUP:9 say "enable C3D Bridge Helper". The helper never calls `AXIsProcessTrustedWithOptions` with a prompt (grep of `helper/Sources` finds none), so macOS will not list it until the user adds it by hand with the "+" button. Nothing says where the app is. Default location: `~/Library/Application Support/Cheetah3D/MCP/helper/C3D Bridge Helper.app`, or `/Applications` for the cask.
- Fix (README step 3 and SETUP:9): "Open System Settings > Privacy & Security > Accessibility. If 'C3D Bridge Helper' is not listed, click `+` and choose `~/Library/Application Support/Cheetah3D/MCP/helper/C3D Bridge Helper.app` (Cmd+Shift+G in the file picker to paste the path), then switch it on. Re-run `npx -y c3d-mcp doctor`."
- Related: state that the helper is started automatically by the server (`open -g -a`). The docs never say it, and users will look for a menu-bar app.

## MAJOR

### M1. TROUBLESHOOTING.md maps error codes wrongly and omits most codes
- `docs/TROUBLESHOOTING.md:7`: `BRIDGE_NOT_INSTALLED` is thrown only when mailbox files or the secret are missing (`bridgeClient.ts:103`). "Installed but not restarted" produces `TRIGGER_FAILED` (menu item not found), per the helper table in `docs/helper.md`. Rewrite as two rows:
  - `| BRIDGE_NOT_INSTALLED | Bridge files or secret missing | Run `npx -y c3d-mcp install` (or the `c3d_install_bridge` tool), then restart Cheetah3D. |`
  - `| TRIGGER_FAILED "menu item ... not found" | Macro installed but Cheetah3D not restarted | Quit and relaunch Cheetah3D. The item is at Tools > Script > Macro Script > C3D-MCP > C3D-MCP Bridge.js. |`
- Line 14 (RUNTIME_STUCK): the code hint (`bridgeClient.ts:282`) says "restart Cheetah3D", but the doc says "close and reopen the document". Use: "Check Cheetah3D for a stuck script or dialog. If nothing is running, restart Cheetah3D."
- Line 13 (APP_BUSY): add the second cause, "another c3d-mcp server holds the bridge lock (`lock.ts:113`). Wait for the other client, or quit it. A lock left by a crashed server is reclaimed automatically." Also say "do not touch Cheetah3D while a call runs".
- Missing codes that exist in `toolkit.ts:5-10` and that users will see: `APP_NOT_RUNNING`, `TIMEOUT`, `CANCELLED`, `CONFIRMATION_REQUIRED`, `UNSUPPORTED`, `AMBIGUOUS`, `NOT_FOUND`, `SCRIPT_ERROR`, `LINT_BLOCKED`, `DEPENDENCY_FAILED`, `NOT_AVAILABLE_IN_PROFILE`, `PARSE_ERROR`, `INTERNAL`. Suggested rows:
  - `APP_NOT_RUNNING | Cheetah3D is not running | Start Cheetah3D and open a document.`
  - `TIMEOUT | The request was discarded and will not run later | Retry. Raise the client's tool timeout for renders (Codex `tool_timeout_sec`, Gemini `timeout`).`
  - `CONFIRMATION_REQUIRED | Destructive action and the client cannot ask you | Re-run with `confirm:true` after you agree.`
  - `UNSUPPORTED | Documented limitation (see limitations.md) or the helper is missing | Follow the `hint`.`
  - `AMBIGUOUS | Several objects share a name | Use the object's `id` from `c3d_list_scene`.`
  - `NOT_AVAILABLE_IN_PROFILE | Tool hidden by C3D_MCP_PROFILE or DISABLE_* | Change the setting and restart the client.`
  - `INTERNAL | Unexpected server error (stack only in the log) | See ~/Library/Logs/c3d-mcp/c3d-mcp.log.`
- Add a section "What to do when the first call fails" (restart the client after editing config, run `npx -y c3d-mcp doctor`, meaning of `[ok]/[warn]/[FAIL]`).

### M2. Config file paths and timeouts disagree between SETUP.md and `config <client>`
- `docs/SETUP.md:33` uses `tool_timeout_sec = 600` and `:38` uses `"timeout": 600000`. The CLI prints 300 and 300000 (`configSnippets.ts` TIMEOUT_SEC=300). The server's render timeout is 15 min (`server.ts` TIMEOUT_MS). Pick one source of truth: have SETUP say "(`c3d-mcp config <client>` prints the same snippet with 300 s; raise it for long renders)".
- `SETUP.md:3`: "`node /path/to/dist/cli/main.js serve`" is wrong. No `main.js` exists; the entry is `packages/server/bin/c3d-mcp.js`. Replace with "`node /path/to/node_modules/c3d-mcp/bin/c3d-mcp.js serve`".
- SETUP.md:12-14, Claude Desktop: omits the critical note the CLI prints: GUI apps do not inherit the shell PATH, so `npx` is often not found. Add: "If Claude Desktop shows 'spawn npx ENOENT', use `npx -y c3d-mcp config claude-desktop --form absolute`, paste that snippet, and restart Claude Desktop." Also say "merge into the existing `mcpServers` object, then quit and reopen Claude Desktop".
- SETUP.md:40-43: Cursor and LM Studio are merged. The LM Studio path is never given (CLI: `~/.lmstudio/mcp.json`, via Program > Install > Edit mcp.json), and the project-level `.cursor/mcp.json` is omitted. The `"env": {"C3D_MCP_PROFILE":"local"}` in the example differs from what `config cursor` prints (no env), which confuses people comparing the two. Split into two headings and mark the env line "optional, for small local models".
- SETUP.md:18-23, Claude Code: `claude mcp add c3d -- ...` adds at local scope by default. Mention `-s user` for all projects, or `.mcp.json` for a project. Warn that installing the plugin AND running `claude mcp add` registers the server twice (plugin/.mcp.json also defines `c3d`).
- SETUP.md:44-52, env table lists 5 of 11 variables. Add `C3D_MCP_TRIGGER=auto|helper|osascript`, `C3D_MCP_DIR`, `C3D_CHEETAH_SUPPORT_DIR`, `C3D_MCP_LOG_DIR`, `C3D_MCP_LOG_LEVEL`, `C3D_HELPER_APP`. Give the default for `C3D_MCP_WORKDIR`: `~/Library/Application Support/Cheetah3D/MCP/tmp`. It is where renders, checkpoints, exports and assets land, and no doc says so.
- `--help` Environment line (`cli/index.ts:43`) omits `C3D_MCP_LOG_LEVEL` and `C3D_HELPER_APP`. `config` accepts `--form`, but the help lists it only under Options. Fine, but add "`doctor --brief`" to the README, since the plugin hook uses it.

These mean nothing to a model or a user and burn tokens. Drop the "(probe Pxx)" and "Verified in probe P07; other formats are not produced" fragments.
